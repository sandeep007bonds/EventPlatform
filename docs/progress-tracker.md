The waiting-room state itself is deliberately Redis-only, not Postgres — a FIFO sorted set per event plus TTL'd admission markers (`RedisQueueStore`, mirroring `RedisHoldStore`'s Lua-script pattern), a genuine asymmetry with ADR-0025's durable scan cache since a lost queue position is just "back of the line," not a broken check-in. `QueueAdmissionController` (a `BackgroundService` mirroring `ExpiredHoldReaper`) promotes waiting sessions via `ZPOPMIN` (atomic, so concurrent replicas can never double-promote) and mints an HMAC-signed admission token per session. `HoldService.PlaceHoldAsync` gains one more settings-derived check (`PlaceHoldOutcome.QueueAdmissionRequired`) verifying that token **locally** (`HmacQueueAdmissionTokenValidator`, shared secret `QueueAdmission:HmacKey`) — zero call back to Queue at hold time, the same "propagate once, verify locally" philosophy ADR-0025 established for Ticketing's scan. Frontend: a new anonymous `QueueWaitingRoomPage` (join/poll, no max-attempts cap unlike ticket polling, sessionStorage-backed session id so a refresh resumes position) that `EventDetailPage`'s "Select seats" now routes through when `requiresQueue` is set, and `SeatSelectionPage` defends against a direct URL hit the same way.
  - ⬜ Replay/one-time-use enforcement on an admission token — not built; a hold's own capacity/limit checks are the accepted backstop this pass
- ✅ **Ticket cancellation & refund workflow (closes the P5 deferred item below):** buyer-initiated `POST /v1/orders/{id}/cancel` (Ordering, gateway-routed), a new `CancelOrderWorkflow` Dapr Workflow saga mirroring `CheckoutWorkflow`'s shape but with a deliberately different step order — void tickets → release sold inventory → refund → mark refunded (unwinding a *completed* sale takes back the product before returning the money, the opposite of `CheckoutWorkflow`'s compensation order, which unwinds a checkout that never finished). Inventory gained `HoldService.CancelSoldAsync` (`POST /v1/holds/{holdId}/cancel`, internal/saga-only) — the reverse of `ConvertToSoldAsync`, releasing sold seats/GA quantities back to available with the same single-status-gate idempotency (`HoldStatus.Cancelled`), extending `GeneralAdmissionAllocation`/`InventoryItem` with `ReleaseSold`. Ticketing gained `TicketVoidingService.VoidByOrderAsync` (`POST /v1/orders/{orderId}/tickets/void`, internal) — all-or-nothing across an order's tickets, mirroring `SeatBlockingService`'s precedent (any already-checked-in ticket blocks voiding the whole order). Payments needed **zero** changes — `RefundActivity`/`IPaymentClient.RefundAsync`/`POST /v1/payments/refund` were already fully built and unused outside saga compensation; this wires them into a real buyer-facing path for the first time. Frontend: `OrderPage` gets a "Cancel order" button (visible only while `Confirmed`) behind an Ant `Modal.confirm`, mapping `NotConfirmed`/`TicketAlreadyCheckedIn`/`Failed` to distinct messages.
  - ⬜ A dedicated Redis instance for Queue in production (dev shares Inventory's) — flagged, not built
  - ⬜ Bot/automation defense at the queue-join step (rate-limiting, CAPTCHA) — not built, a real hardening gap for a genuine high-demand on-sale
  - ⬜ Randomized queue-position ordering — current implementation is strict FIFO only; the enterprise requirements doc asks for an option to randomize positions at queue-open (e.g. to avoid rewarding whoever scripts the fastest join), not built
  - ⬜ Abandoned-waiting-session expiry — `SessionTtlSeconds` only expires an *admitted* session's token; a session that joins the waiting sorted set and never returns has no TTL at all today and sits in Redis indefinitely, unlike Inventory's `Hold`, which has `ExpiredHoldReaper` for exactly this kind of abandonment
- ✅ **Manual sales pause/resume (ADR-0027, closes the P6 deferred item below):** a new `Event.SalesPaused` bool (Catalog) lets an organizer halt/resume new holds for an already-`Published` event on demand — independent of the static `OnSaleAt`/`BookingEndsAt` window, and without touching already-placed holds/tickets. `PauseSales`/`ResumeSales` vertical slices (`POST /v1/events/{id}/pause-sales`/`resume-sales`, same tenant-ownership/409-conflict shape as `PublishEvent`) publish new `EventSalesPaused`/`EventSalesResumed` integration events — not a redelivered `EventPublished` (dead path — `InventoryProvisioningService.ProvisionAsync`'s idempotency guard would just short-circuit) or the zero-consumer `EventUpdated`. Inventory's new `EventSalesToggleService` consumes both via two new Dapr subscriptions, updating `EventInventorySettings.SalesPaused` directly; `HoldService.PlaceHoldAsync` checks it first, before the on-sale/booking-cutoff checks (`PlaceHoldOutcome.SalesPaused`, 409). Frontend: a "Pause sales"/"Resume sales" toggle on `AdminEventDetailPage` (rendered only for `Published` events), buyer-facing gating in `EventDetailPage`/`SeatSelectionPage` mirroring the existing `onSaleAt` pattern exactly.
  - ⬜ Gate/doors-open time and price changes post-publish remain out of scope — both need real propagation redesign (Ticketing's scan-window cache and Inventory's baked-in seat/GA price are both populated once at publish and never re-read), see ADR-0027's Alternatives.
- ✅ **Frontend: inline tour creation + upcoming/past legs on `CreateEventPage`:** organizer feedback that creating a tour was a disconnected, separate-page flow from creating its first leg. `EventGroupPicker` dropped its instant-create modal (which called `POST /v1/event-groups` the moment "+ New tour" was picked, immediately, even if the form was later abandoned) in favor of a plain `Select`; `CreateEventPage` now renders either an inline "New tour title" field (deferring tour creation to the event's own submit — no orphan tour if abandoned, and the new tour inherits this first leg's own dates as its advertised range) or, when an existing tour is picked, a new `TourLegsList` (upcoming legs always visible, past ones collapsed behind a count toggle) so the organizer sees what's already scheduled before adding another. `TourLegsList` is reused on `AdminEventDetailPage` (a "Part of a tour" card, once an event has one) and `AdminEventsPage` gained a "Tour" column (client-side batched `getEventGroup` lookups over the current page's distinct ids — Catalog has no batch endpoint for this). `CreateEventGroupPage` (`/admin/tours/new`) is unchanged, still the only way to set a tour's full details (contact/social, wider date range) after creation.
  - ⬜ Still no UI to edit an already-created tour's contact/social (dates gained a small "Edit dates" action on `TourDetailPage` in the multi-leg-repeater pass below) — this pass only touched creation-time and read-only display flows.
- ✅ **Frontend: graceful load-failure states, no more stacked error toasts:** a failed data fetch (backend down, network error) was showing up to 4 stacked toasts on one page load — the axios interceptor's own generic 5xx/network toast plus the page's own `toast.error('Could not load X.')`, doubled again by React StrictMode's dev-mode double-invoke — while the page's "No events found" empty state rendered underneath anyway, making a real failure indistinguishable from a genuine empty result. `httpClient`'s interceptor no longer auto-toasts at all (401 session-clear is the only status it still handles globally) — every call site, load or action, already had its own specific handler. New `LoadError` (inline Ant `Result`, "Couldn't load this" + retry) replaces the toast on every list/panel's own failed load (`EventsListPage`, `AdminEventsPage`, `EventGroupsPage`, `MyOrdersPage`, `AdminOrdersPage`, `SeatBlockPanel`, `TourLegsList`), tracked as its own `loadError` state distinct from "succeeded with zero results." Single-resource detail pages (`EventDetailPage`, `AdminEventDetailPage`, `OrderPage`) now check `error.response?.status === 404` to show `NotFoundPage` only for a genuine 404, `ServerErrorPage` (previously reserved for route-level render errors only) for anything else — previously *any* failure on those pages, including a network error, showed the misleading "not found" message. Action-triggered toasts (save, publish, block/unblock, login) are unchanged.
- ✅ **Frontend: tour-first flow — `TourDetailPage` + "Add leg" (superseded below):** the inline quick-create above was still event-first; organizer feedback wanted tour-first instead — create the tour, land on its own page, keep adding legs from there. New `TourDetailPage` (`/admin/tours/:id` — dates/contact summary + `TourLegsList`) gets an "Add leg" button linking to `CreateEventPage?eventGroupId=<id>`, which now reads that query param via `useSearchParams` to pre-fill the tour picker. `CreateEventGroupPage` now lands on the new tour's own page instead of the list; `EventGroupsPage`'s rows are clickable through to the same page. The inline "+ New tour" fast path on `CreateEventPage` itself is unchanged and still available for the "already creating an event, realize it needs a tour" case. **This one-leg-at-a-time-via-navigation shape turned out not to match the actual ask** — see the next bullet.
- ✅ **Frontend: single-page multi-city leg repeater on `CreateEventPage` (replaces the per-leg-navigation flow above):** the tour-first flow still made adding several legs a repeated navigate-away-and-back cycle; the actual requirement was one page/form that defaults to a plain single-event form and grows inline into a multi-leg batch via an "Add" action, all submitted together in one visit — e.g. "Event X plays 4 cities next week" becomes 4 leg cards on one page, not 4 separate page visits. New `EventLegFields` (`Form.List name="legs"`, one `Card` per city/date, mirrors `SeatMapSectionsFields.tsx`'s repeater shape exactly) replaces `CreateEventPage`'s single set of event fields; "Add another city/date" appends another card and, once there's more than one leg, the tour picker becomes required (auto-switching to "+ New tour" if nothing was picked yet — a multi-leg batch always needs somewhere to attach). Submission creates the tour first if needed, then calls `POST /v1/events` **sequentially** (never in parallel — the server's sibling-overlap check re-queries fresh state per call) and backfills a newly-created tour's date range from `min`/`max` across the submitted legs afterward. **No rollback exists for a partial failure** (no delete endpoint for `Event`/`EventGroup`), so each leg's status (`pending`/`created`/`failed`) is tracked and shown inline — already-created legs lock and tag themselves, the submit button relabels to "Create remaining legs," and a retry only (re-)submits what's left. `TourDetailPage`'s "Add leg" and `CreateEventGroupPage` are unchanged in purpose (still the way to set a tour's full metadata up front, or add exactly one more leg later) — both now funnel into this same repeater-capable page rather than a single-leg-only form. `TourDetailPage` also gained a small "Edit dates" action (`Modal` + `updateEventGroup`) — closes a real, separately-noted gap (there was previously no way to edit a tour's dates at all) surfaced while wiring this pass's own date-range-backfill fallback message.
